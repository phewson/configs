** Geller Cycling Infrastructure, Geller Categories and Active Lives Data

*** Motivation

Roger Geller's cyclist typology suggests that differences between cyclists are largely driven by tolerance for traffic stress rather than destination choice. The key groups are:

- Strong and Fearless
- Enthused and Confident
- Interested but Concerned
- No Way No How

Most infrastructure metrics (e.g. km of cycle lanes per capita) do not distinguish between the needs of these groups. A city may have substantial cycling infrastructure but still provide poor connectivity for more cautious cyclists.

The objective is to develop city-level indicators describing how well a city serves different cyclist types and assess whether these indicators are associated with cycling participation reported in the Active Lives Survey.

*** Data Sources

**** OpenStreetMap

Use OSM to construct a routable transport network and identify:

- road classifications
- cycle tracks
- painted cycle lanes
- shared-use paths
- traffic-free routes
- speed limits
- surface types
- one-way restrictions

**** Census 2021 Origin-Destination Data

Use commuting OD matrices to identify likely travel demand between areas.

Potentially use these data:
- directly as demand weights
- or within a simple traffic assignment model to estimate relative traffic volumes on roads

**** Active Lives Survey

Use cycling participation rates as outcome variables.

Possible dependent variables:
- overall cycling participation
- female cycling participation
- older adult cycling participation
- participation among less active groups

The expectation is that infrastructure suitable for "Interested but Concerned" cyclists may be more strongly associated with these groups than with already confident cyclists.

**** Terrain Data

Previous work has shown that hilliness is associated with lower cycling levels.

Potential extensions:
- revisit this relationship in the context of e-bike adoption
- measure hilliness along likely cycling routes rather than for whole local authorities

*** Network Construction

Load OSM into PostgreSQL/PostGIS (e.g. via osm2pgsql).

Create an edge table with fields such as:

- edge_id
- from_node
- to_node
- length
- road_class
- speed_limit
- cycleway_type
- surface
- gradient
- assigned_flow (optional)
- stress_score

Avoid hard-coding cyclist types initially. Instead create a generic stress score that can later be reclassified.

*** Stress Classification

Assign each edge a cycling stress score based on:

- road hierarchy
- speed limit
- cycling provision
- inferred traffic volume
- gradient

Example scale:

0 = traffic-free route
1 = protected cycle track
2 = quiet residential street
3 = painted cycle lane
4 = busy urban road
5 = major arterial road

*** Geller Networks

Create separate networks for different cyclist types.

**** Strong and Fearless

Almost all roads except motorways.

**** Enthused and Confident

Exclude the highest-stress roads.

**** Interested but Concerned

Restrict to:
- protected infrastructure
- traffic-free routes
- quiet residential streets

**** Very Cautious Cyclists

Only:
- fully separated routes
- traffic-free facilities

These can be implemented as filtered views of the same edge table.

** Casuality * Idea: Quantifying the Value of Additional Variables in STATS19/STATS20

*** Motivation

Current STATS19 records all drivers involved in reported injury collisions, but
passenger information is incomplete. Passengers who are present but uninjured
are generally not observed in the dataset.

This creates a partially observed occupancy variable:

\[
O_i = \text{true occupancy of vehicle } i
\]

while the observed data contain only:

\[
Y_i = \{\text{driver information, collision details, injured casualties}\}.
\]

The immediate application is estimating the effect of carrying passengers on
collision risk, but the broader question is:

#+begin_quote
How much information would be gained by recording a currently unobserved
variable?
#+end_quote

This reframes STATS20 design as a statistical decision problem rather than a
simple data collection problem.

*** Passenger Presence as a Missing Data Problem

The key issue is not missing collision data but missing occupancy data.

Let:

\[
P_i = 1
\]

if a passenger was present.

In current STATS19, a passenger is typically observed only when they become a
recorded casualty:

\[
ObservedPassenger_i = P_i \times I_i
\]

where

\[
I_i = 1
\]

if the passenger is injured.

Thus many vehicles with passengers are indistinguishable from vehicles with no
passengers.

*** Why STATS19 Alone Cannot Identify Passenger Effects

The desired quantity is something like:

\[
P(Collision \mid do(Passenger = 1))
\]

compared with

\[
P(Collision \mid do(Passenger = 0)).
\]

However STATS19 contains only injury collisions, not the non-collision exposure
population.

In practice it provides information about:

\[
P(Passenger \mid Collision)
\]

rather than

\[
P(Collision \mid Passenger).
\]

Consequently occupancy effects are not identifiable from STATS19 alone.

*** Role of the National Travel Survey

The National Travel Survey (NTS) provides exposure information for the travelling
population, including:

- vehicle occupancy rates;
- journey purposes;
- age and sex distributions;
- passenger travel frequency.

This allows estimation of:

\[
P(O)
\]

or more generally

\[
P(O \mid X)
\]

for demographic and journey covariates \(X\).

Combining NTS and STATS19 creates a case-population design where:

- NTS provides exposure;
- STATS19 provides collision outcomes.

*** Using Collision Geometry to Recover Occupancy Information

A potentially useful identification strategy is based on impact location.

For a right-hand-drive vehicle:

- left-side impacts disproportionately affect nearside passengers;
- right-side impacts disproportionately affect drivers.

If a passenger is present, a left-side impact increases the probability that the
passenger becomes an observed casualty.

This can be represented as:

\[
O_i \rightarrow C_i
\]

\[
Impact_i \rightarrow C_i
\]

where \(C_i\) denotes observed passenger casualties.

Collision geometry therefore changes the observation probability without
necessarily changing occupancy itself.

This provides partial information about otherwise unobserved passengers.

*** Latent Occupancy Model

A Bayesian latent-variable model could treat occupancy as unobserved.

Estimate:

\[
P(O_i \mid D_i)
\]

where \(D_i\) contains:

- driver age;
- driver sex;
- vehicle type;
- collision type;
- impact location;
- road characteristics;
- time of day;
- casualty records.

NTS data provide informative priors on occupancy patterns.

The analysis would estimate occupancy probabilities rather than assuming
occupancy is known.

*** Main Contribution: Value of Information

The most interesting research question may not be the passenger effect itself.

Instead:

#+begin_quote
What is the value of collecting occupancy information directly?
#+end_quote

Compare three scenarios.

**** Scenario 1: Current STATS19

Occupancy partially observed.

Inference based solely on existing records.

**** Scenario 2: Enhanced Inference

Occupancy inferred using:

- STATS19;
- collision geometry;
- NTS priors.

**** Scenario 3: Full Occupant Recording

Occupancy observed directly for all vehicle occupants.

This represents a hypothetical STATS20.

*** Measuring Information Gain

Possible measures:

- posterior variance;
- credible interval width;
- Shannon entropy;
- uncertainty in policy-relevant parameters.

For example:

\[
Var(\theta_{occupancy})
\]

or

\[
Var(RR_{passenger})
\]

under each scenario.

The value of the new variable is then:

\[
VOI =
Uncertainty_{current}
-
Uncertainty_{enhanced}
\]

for an appropriate uncertainty measure.

*** Possible Outcomes

The study may find:

1. occupancy is already recoverable from existing variables and additional
   collection adds little information;

2. occupancy becomes much more certain with direct recording;

3. occupancy becomes certain but causal estimates remain uncertain because of
   confounding (e.g. trip purpose);

4. some other variable would be more valuable to collect than occupancy.

A useful result could therefore be:

#+begin_quote
Recording occupancy would reduce uncertainty in occupancy prevalence by 80% but
reduce uncertainty in passenger-risk estimates by only 10%.
#+end_quote

Such findings would directly inform data collection policy.

*** Broader Framework

This framework could be applied to any candidate STATS20 variable:

- occupancy;
- seatbelt use;
- distraction indicators;
- journey purpose;
- mobile phone use;
- other behavioural variables.

The general principle is:

#+begin_quote
The objective is not to determine whether a variable is useful, but whether it
is sufficiently informative to justify collection.
#+end_quote

*** Potential Journal Targets

If framed as a transport application:

- Accident Analysis & Prevention
- Traffic Injury Prevention
- Transportation Research Part F
- Journal of Safety Research

If framed as a methodology for evaluating administrative data collection:

- JRSS Series A
- Journal of Official Statistics
- Journal of Survey Statistics and Methodology
- International Statistical Review
- Statistics and Public Policy

The stronger methodological contribution is likely the value-of-information
framework rather than the occupancy case study itself.

*** Working Title Ideas

- Quantifying the Value of Additional Variables in Road Collision Reporting Systems
- How Much Information Is Occupancy Worth? A Value-of-Information Analysis for STATS19
- Evaluating Candidate Variables for STATS20 Using Bayesian Missing-Data Models
- Information Gain from Enhanced Occupant Recording in Road Collision Data

It is very common to get "tangled in the wires" once you move from single scripts to a structured software project. Using consistent terminology will help you distinguish between the "How" (the logic) and the "When" (the pipeline).

Here is a breakdown of the standard engineering terms you can use in your lab notes:
1. The "Logic Core" (Module Files)
 -  Terminology: "Modules" or "Library Code."
-  Location: course/regression/regression_core.py etc.
- Role: These contain pure, stateless functions.
 The "Why": These are Testable. They don't depend on CLI arguments or specific file paths (they just take data and return objects), you can point pytest at them easily.

  Analogy: This is the Engine. It’s built on a workbench and tested in isolation.

2. The "Entry Points" (Script Files)
- Terminology: "CLI Scripts" or "Driver Scripts."
- Location: e.g. course/scripts/02_fit_model.py.
- Role: These are the "thin wrappers." They handle the "plumbing"—parsing command-line arguments (via Click), loading CSVs, calling the module functions, and saving the output.
The "Why": They aren't really meant for unit testing; they are for Execution.

Analogy: This is the Dashboard/Ignition. It’s how the user actually interacts with the engine.

3. The "Pipeline" (dvc.yaml)
- Terminology: "The Orchestrator" or "The Workflow Definition."
- Role: It defines the Lineage. It tells DVC: "To get Output C, you must run Script B using Data A."
- The "Why": It provides Reproducibility.
Analogy: This is the Assembly Line. It ensures every step happens in the right order and only re-runs if something has changed.

Comparison Table
 | Feature	Modules (course.blah) | Driver Scripts (02_*.py) | Orchestrator (dvc.yaml) |                       |
 | Primary Goal                  | Define Logic             | Execute Logic           | Link Logic & Data     |
 | Key Action                    | def fit_model(...)       | click.command()         | cmd: python script.py |
 | Testing                       | Unit Tests (pytest)      | Integration Tests       | End-to-End Pipeline   |
 | Analogy                       | The Tool                 | The Hand using the Tool | The Project Blueprint |

    "We put the hard math in the Modules so we can test it. We put the file-saving in the Scripts so we can run it. We put the scripts in the Orchestrator so we never have to remember the order of operations."   This "Separation of Concerns" is what separates a Data Scientist who writes "one-off" code from a Data Engineer who builds systems. You aren't just teaching them Regression; you're teaching them System Architecture.


Mastering the Pipeline: An Introduction to DVC

Welcome to the course! To manage our data science workflows, we use a tool called DVC (Data Version Control). While DVC can do many complex things, we use it primarily as a build system to ensure your analysis is reproducible, traceable, and organized.
1. Getting Started: Environment First

Before you type a single DVC command, you must activate your environment. DVC and all the necessary libraries (like pandas and scikit-learn) live there.
Bash

conda activate your_env_name

2. Understanding dvc.yaml

Think of dvc.yaml as the "recipe book" for your project. It defines Stages. Each stage tells DVC:

    Command (cmd): What script to run.

    Dependencies (deps): What files must exist (or haven't changed) for this to work.

    Outputs (outs): What file the script will create (dataframes, models, or plots).

    Important: If DVC tells you to "commit your artefacts to Git," ignore it. We use DVC specifically so that large data files (artefacts) stay out of our GitHub repository.

3. The Big Three: dag, repro, and force
Visualizing the Flow: dvc dag

To see how your scripts connect, run:
Bash

dvc dag

This prints a "Directed Acyclic Graph"—a map showing how data flows from your SQL queries through to your final report.
Running the Pipeline: dvc repro

This is your primary command. When you run dvc repro, DVC checks your dependencies. If you've changed a script or a data file, it re-runs only the necessary stages.

    Partial Success: If your pipeline fails at Stage 3, DVC remembers that Stages 1 and 2 are finished. You don't have to start over!

Starting Fresh: dvc repro -f

If you want to force DVC to re-run a specific stage (even if it thinks nothing has changed), use the force flag:
Bash

dvc repro <stage_name> --force

4. Development Workflow: Scripts vs. Modules
Developing Scripts

While DVC handles the automation, you are encouraged to run scripts manually while debugging:
Bash

python course/scripts/02_eda.py --input-csv data/toy.csv

You can also import your module code into a Jupyter Notebook to experiment with visualizations or model parameters before "baking" them into the pipeline.
The "Engine Room": core.py

Most of the heavy lifting is done in the module files (e.g., course/supervised_classification/core.py).

    Read the Docstrings: I have provided detailed instructions inside the functions.

    Pass the Tests: Use the provided unit tests to verify your logic.

    Run the Pipeline: Once your code passes the tests, dvc repro should sail through to completion.

5. A Note on Naming: The "Click" Translation

We use a library called click to handle command-line arguments. There is one golden rule to remember:

    In the Terminal (DVC YAML): We use hyphens, e.g., --data-csv.

    In the Python Function: We use underscores, e.g., data_csv.

Python cannot use hyphens in variable names, so Click automatically translates them for you!
6. Extra Credit and Customization

Walk before you run. 1.  Complete the existing pipelines (Unsupervised, Supervised, and Regression) exactly as they are defined.
2.  Once your final_report.html is looking perfect, you may consider adding extra credit features:
* Modifying the SQL queries.
* Adding extra classification scripts (e.g., Random Forest).
* Adding new stages to dvc.yaml.

Good luck! Lean on dvc status to see what needs work, and trust the pipeline.
